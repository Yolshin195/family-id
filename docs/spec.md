# family-id — техническое задание

Статус: **черновик на согласование** (этап 0). Код пишется только после одобрения.
Связанные документы: [план по этапам](plan.md), [ADR](adr/README.md).

family-id — собственный сервис регистрации и входа: провайдер OpenID Connect и сервер авторизации OAuth 2.1
для моих проектов, с бесшовным входом между ними. Первый клиент — «Семейная бухгалтерия»
(`Yolshin195/family-budget`). Сервис заменяет Rauthy.

Обозначения: `<домен>` — корневой домен из конфигурации (например, `example.com`), сервис работает на
`id.<домен>`. MUST/SHOULD в цитатах из стандартов не переводятся.

## 0. Принятые решения

Ответы на «Открытые решения» и вопросы, возникшие при разборе задачи (15.10.2026).

| # | Вопрос | Решение | Где подробно |
| --- | --- | --- | --- |
| 1 | Домен и `rpId` | Домен не зашит в код, задаётся конфигурацией. Сервис — `https://id.<домен>`, `rpId` passkey — корневой `<домен>` | [ADR-0003](adr/0003-domain-and-rp-id.md) |
| 2 | Регистрация только по passkey | Разрешена. Telegram — в v1.1 (как в таблице этапов) | §3 |
| 3 | Email | Код на email переносится на **v2**. До v2 у сервиса нет SMTP, а у пользователей — почты | [ADR-0009](adr/0009-no-email-until-v2.md) |
| 4 | Лицензия | Публичный репозиторий, `MIT OR Apache-2.0` | — |
| 5 | Алгоритм подписи | EdDSA (Ed25519) по умолчанию и RS256: его требует OIDC Discovery, и он нужен Conformance Suite | [ADR-0002](adr/0002-signing-keys.md) |
| 6 | Бухгалтерия без email | Доработку бухгалтерии делаем позже, отдельно. Здесь — только описание в `docs/integrate.md`. Фокус этого репозитория — безопасность и удобство | §17 |
| 7 | Аватары | Картинки на сервер не загружаются. Аватар — инициалы на цветном круге, `picture` в токенах не выдаётся | §3.1 |

Изменения относительно исходной задачи, вытекающие из этих решений и из стандартов:

- **`prompt=none`, `max_age`, `prompt=login` переходят из v1.1 в v1.** Без них не проходит план Conformance Suite
  «Basic OP», который является критерием готовности v1.
- **Код на email — v2, а не v1.1.**
- **Тестовый вход для Conformance Suite.** Браузер-робот Suite (HtmlUnit) не умеет WebAuthn. Для автоматического
  прогона нужен тестовый способ входа, которого физически нет в боевой сборке ([ADR-0008](adr/0008-conformance-login.md)).
- **Telegram: `sub` — не числовой id.** По описаниям интеграций (официальная страница из контейнера недоступна —
  §19), `sub` у Telegram непрозрачный и свой для каждого бота, числовой id приходит в claim `id` (scope `profile`).
  UserInfo у Telegram нет. Мы связываем аккаунт по паре (`iss`, `sub`) — это корректно и так.

## 1. Цели и границы

### 1.1. Для кого

- Семья (Таиланд и русскоязычные) и, возможно, внешние пользователи моих сайтов. Регистрация открытая.
- Владелец (я) — администратор: командная строка в v1, админ-страницы в v2.
- Мои приложения — клиенты OIDC (первым — бухгалтерия).
- AI-ассистенты — клиенты OAuth для MCP-серверов моих приложений (сначала только Claude).

### 1.2. Что считаем успехом

1. **Регистрация — два шага:** имя → Face ID / Touch ID. Без паролей, почты и подтверждений.
2. **Вход — одно касание:** passkey подставляется сам (conditional UI), без ввода логина.
3. **Единый вход (SSO):** вошёл в одном приложении — в остальных вход происходит без нажатий.
   **Единый выход:** вышел в одном — сессии во всех приложениях этого браузера закрываются; «Выйти везде» в
   кабинете закрывает все сессии аккаунта на всех устройствах и во всех приложениях.
4. **Три языка** на всех страницах, в сообщениях об ошибках и в датах.
5. **Безопасность:** OWASP ASVS 5.0 уровня 2, OAuth 2.1 и RFC 9700, сертификационные профили OpenID Conformance
   Suite проходят в CI.
6. **Лёгкость:** один контейнер, < 64 МБ RAM в покое, своя база в существующем PostgreSQL 16.

### 1.3. Чего не делаем

- Паролей — ни при регистрации, ни для восстановления.
- Автосклеивания аккаунтов по совпадению email, имени или телефона.
- Открытой динамической регистрации клиентов (RFC 7591) — в MCP 2026-07-28 она устарела.
- Implicit, hybrid, password и client_credentials grant; токенов в query string; секретов у публичных клиентов.
- Front-channel logout и OIDC Session Management (`check_session_iframe`): браузеры режут сторонние cookie, мы
  используем back-channel.
- Запросов `request` / `request_uri` (JAR), `claims` и PAR в v1 (объявляем как неподдерживаемые; PAR — кандидат на
  потом).
- Загрузки картинок и любых пользовательских файлов.
- Кластера: один экземпляр сервиса. Лимиты и кэши живут в памяти процесса (§14).

## 2. Термины

| Термин | Значение |
| --- | --- |
| Аккаунт | Пользователь family-id. Идентификатор для приложений — `sub` (UUID, не меняется, не зависит от способа входа) |
| Способ входа | Passkey, связанная учётка Telegram (v1.1), позже email-код и другие провайдеры. У аккаунта ≥ 1 способа |
| Сессия (SSO-сессия) | Вход в family-id в конкретном браузере. Публичный идентификатор — `sid`; cookie хранит случайный секрет, в БД — его хеш |
| Клиент | Приложение, которое получает токены: OIDC-клиент из конфигурации, предзаведённый публичный клиент или клиент по CIMD |
| Ресурс | MCP-сервер приложения, для которого выдаётся access-токен (RFC 8707); заведён в конфигурации, у него есть приложение-владелец |
| Грант | Разрешение аккаунта клиенту: набор `scope`, ресурс, claims от приложения-ресурса. На гранте держатся refresh-токены |
| Поток входа | Незавершённый запрос авторизации, ожидающий входа или согласия пользователя (10 минут) |
| Свой клиент | Клиент из конфигурации с `first_party = true` (мои приложения): согласие не спрашивается |

## 3. Аккаунт и способы входа

### 3.1. Аккаунт

| Поле | Правила |
| --- | --- |
| `sub` | UUID v4, генерируется при регистрации, никогда не меняется и не переиспользуется |
| Имя (`name`) | Обязательно, 1–64 символа после нормализации (Unicode NFC, обрезка пробелов, без управляющих символов) |
| Имя пользователя (`preferred_username`) | Необязательно; 3–32 символа `[a-z0-9_.]`, уникально без учёта регистра; задаётся в кабинете. Для входа не используется |
| Язык (`locale`) | `ru` / `en` / `th`; при регистрации — язык страницы |
| Тема | `system` / `light` / `dark` |
| Аватар | Не хранится. Страницы рисуют инициалы на круге, цвет — детерминированно от `sub`. Claim `picture` не выдаётся |
| Email | До v2 отсутствует. В v2 — только подтверждённый кодом, и только тогда выдаётся в `email`/`email_verified` |
| Статус | `ACTIVE` / `DISABLED` (блокировка администратором). Удаление — физическое (§3.6) |

### 3.2. Способы входа по версиям

| Способ | Версия | Признак в `amr` (RFC 8176) | Сильный вход |
| --- | --- | --- | --- |
| Passkey с проверкой пользователя, синхронизируемый (флаг BE = 1) | v1 | `["swk", "mfa"]` | да |
| Passkey с проверкой пользователя, привязанный к устройству (BE = 0) | v1 | `["hwk", "mfa"]` | да |
| Telegram | v1.1 | `["fed"]` | нет |
| Ссылка восстановления от администратора | v1.1 | не выдаётся: ссылка даёт только сессию восстановления (§3.5) | — |
| Код на email | v2 | `["eml"]` | нет |
| Google, LINE, Apple (OIDC), GitHub, Facebook (OAuth2) | v2 | `["fed"]` | нет |
| Тестовый вход Conformance Suite | только сборка `conformance` | `["pwd"]` | нет |

- Аттестация не запрашивается, поэтому про аппаратность ключа мы знаем только флаг Backup Eligible
  из authenticator data: синхронизируемый passkey (iCloud Keychain, Google Password Manager) → `swk`,
  привязанный к устройству (ключ безопасности, TPM) → `hwk`. Проверка пользователя (UV: биометрия или PIN
  устройства) обязательна для всех passkey, поэтому вместе с владением ключом это два фактора → `mfa`.
- `fed` и `eml` не зарегистрированы в реестре IANA, RFC 8176 это допускает по соглашению сторон. Значения выбраны
  так, чтобы ни одно не попадало в список второго фактора бухгалтерии (`mfa`, `otp`, `hwk`, `swk`, `sms`, `fpt`,
  `face`, `iris`, `pop`). Telegram сознательно не получает `pop`: бухгалтерия засчитала бы его вторым фактором.
- `amr` описывает **последнюю аутентификацию** в сессии. Если сессия начата через Telegram, а потом пользователь
  подтвердил вход passkey (повторная аутентификация или `prompt=login`), `amr` становится passkey-шным.
- Маппинг публикуется в `docs/integrate.md`.

### 3.3. Регистрация (v1)

1. «Создать аккаунт» → поле «Как вас зовут?» → «Создать passkey».
2. Браузер предлагает сохранить passkey (Face ID / Touch ID / Windows Hello / Android). `rp.name` — название
   сервиса из конфигурации, `user.name` и `user.displayName` — введённое имя, `user.id` — случайный 64-байтный
   handle аккаунта (не `sub`).
3. Аккаунт создаётся только после успешного `finish` ceremony: брошенная регистрация следов не оставляет.
4. Сразу после регистрации — мягкое предложение второго способа, с кнопкой «Позже»:
   - v1: «Сохранить passkey ещё на одном устройстве» — инструкция: войти на втором устройстве через
     «другое устройство» (QR от телефона, кросс-девайсный вход встроен в браузеры) и нажать «Добавить passkey на
     этом устройстве»; если passkey синхронизируется (BE = 1), показываем «Ваш passkey уже сохраняется в
     iCloud / Google» и предложение не навязываем;
   - v1.1: плюс «Привязать Telegram».
5. Ограничения: 5 регистраций в час с одного IP, 200 в сутки на весь сервис (настраивается); сверх — 429 и
   понятное сообщение.

Регистрация через Telegram (v1.1): «Войти через Telegram» → если учётка Telegram не связана ни с одним
аккаунтом, создаётся новый аккаунт с именем из Telegram, сразу предлагается добавить passkey.

### 3.4. Вход

- **Автоподстановка (conditional UI).** На странице входа — поле с `autocomplete="username webauthn"`; при фокусе
  браузер показывает сохранённые passkey этого `rpId`. Запрос `navigator.credentials.get({mediation:
  "conditional"})` запускается при загрузке страницы.
- **Кнопка «Войти с passkey»** — модальный запрос (discoverable credentials): логин не вводится, аккаунт
  определяется по `userHandle`.
- **Вход с другого устройства** — встроенный в браузер QR (hybrid transport), ничего делать не нужно.
- Если passkey не найден на сервере (удалён в кабинете) — сообщение «Этот passkey удалён из аккаунта» и вызов
  WebAuthn Signal API `signalUnknownCredential`, чтобы менеджер паролей его скрыл (где API поддерживается).
- После входа — возврат в поток авторизации приложения или в кабинет.

### 3.5. Привязка способов и восстановление

- Новый способ привязывается **только к уже вошедшему пользователю** и требует свежей аутентификации (≤ 10 минут,
  иначе повторный запрос passkey).
- Если учётка Telegram уже связана с другим аккаунтом — отказ с объяснением, без склеивания.
- Нельзя удалить или отвязать последний способ входа.
- **Восстановление:** войти любым другим привязанным способом. Если способов не осталось — одноразовая ссылка
  администратора (v1.1):
  - `family-id recovery-link <sub | имя пользователя>` печатает ссылку `https://id.<домен>/recover/<токен>`
    (256 бит, в БД — хеш), срок 24 часа, одноразовая; создание и использование пишутся в журнал безопасности
    аккаунта;
  - ссылка открывает **сессию восстановления**: в ней можно только создать новый passkey, токены приложениям не
    выдаются. После создания passkey пользователь входит им как обычно (`amr` — passkey). Остальные сессии
    аккаунта при этом закрываются (с back-channel logout).

### 3.6. Удаление аккаунта (v1.1)

Кабинет → «Удалить аккаунт» → свежая аутентификация passkey → подтверждение. Затем:

1. Все сессии закрываются, всем приложениям уходит back-channel logout.
2. Всем приложениям, у которых был грант или сессия этого аккаунта, уходит подписанное событие «аккаунт удалён»
   (§5.3).
3. Удаляются аккаунт, способы входа, гранты, токены, сессии. В журнале остаётся одна запись «аккаунт удалён»
   с `sub` без персональных данных — на год (нужна для разбора инцидентов).

## 4. OpenID Connect провайдер

### 4.1. Discovery и ключи

- `GET /.well-known/openid-configuration` (OIDC Discovery 1.0) и `GET /.well-known/oauth-authorization-server`
  (RFC 8414) — один набор метаданных. `issuer` = `https://id.<домен>` без завершающего `/` и без пути.
- Значения, отличные от очевидных:

| Поле | Значение |
| --- | --- |
| `response_types_supported` | `["code"]` |
| `response_modes_supported` | `["query"]` |
| `grant_types_supported` | `["authorization_code", "refresh_token"]` |
| `subject_types_supported` | `["public"]` |
| `id_token_signing_alg_values_supported` | `["EdDSA", "RS256"]` |
| `code_challenge_methods_supported` | `["S256"]` |
| `token_endpoint_auth_methods_supported` | `["client_secret_basic", "client_secret_post", "none"]` |
| `scopes_supported` | `["openid", "profile"]` (+ `email` с v2; `offline_access` не объявляется) |
| `claims_supported` | `sub`, `iss`, `aud`, `exp`, `iat`, `auth_time`, `nonce`, `amr`, `sid`, `name`, `preferred_username`, `locale`, `updated_at` |
| `authorization_response_iss_parameter_supported` | `true` |
| `request_parameter_supported`, `request_uri_parameter_supported`, `claims_parameter_supported` | `false` |
| `ui_locales_supported` | `["ru", "en", "th"]` |
| `end_session_endpoint`, `backchannel_logout_supported`, `backchannel_logout_session_supported` | v1.1 |
| `revocation_endpoint`, `introspection_endpoint` | v1 |
| `client_id_metadata_document_supported` | `true` с v1.2 |

- `GET /jwks.json` — публичные ключи: Ed25519 (`OKP`, `EdDSA`) и RSA 2048 (`RS256`), `kid` — отпечаток по
  RFC 7638. Кэш у клиентов — `Cache-Control: max-age=600`.
- Алгоритм ID-токена задаётся для каждого клиента (`id_token_signed_response_alg`, по умолчанию `EdDSA`).
  Logout token и события подписываются тем же алгоритмом, что и ID-токены клиента.
- Ротация ([ADR-0002](adr/0002-signing-keys.md)): каждые 90 дней. Новый ключ публикуется в JWKS за 7 дней до
  начала подписи, старый остаётся в JWKS 30 дней после. Ротация вручную — `family-id keys rotate`. Закрытые ключи
  хранятся в БД, зашифрованные мастер-ключом из окружения (AES-256-GCM).

### 4.2. Запрос авторизации `GET|POST /authorize`

| Параметр | Поведение |
| --- | --- |
| `response_type` | Только `code`; иначе `unsupported_response_type` |
| `client_id` | Известный клиент; иначе страница ошибки (не редирект) |
| `redirect_uri` | Точное совпадение с зарегистрированным; для loopback-адресов публичных клиентов — без учёта порта (RFC 8252 §7.3). Неверный → страница ошибки, не редирект |
| `scope` | Должен содержать `openid` для OIDC; неизвестные значения игнорируются |
| `state` | Возвращается как есть |
| `code_challenge`, `code_challenge_method` | Обязательны, только `S256`. Исключение — только клиенты Conformance Suite в сборке `conformance` ([ADR-0008](adr/0008-conformance-login.md)) |
| `nonce` | Необязателен (PKCE защищает от подмены кода); если передан — попадает в ID-токен |
| `prompt` | `none` — без интерфейса: есть сессия и согласие → код, иначе `login_required` / `consent_required`; `login` — всегда повторная аутентификация; `consent` — показать согласие; `select_account` — как `login` |
| `max_age` | Если с `auth_time` прошло больше — повторная аутентификация; `auth_time` всегда в ID-токене |
| `id_token_hint` | При `prompt=none`: `sub` из подсказки ≠ текущему аккаунту → `login_required`. Подпись проверяется, истёкший срок допустим |
| `ui_locales` | Язык страниц (§8.1) |
| `login_hint`, `display`, `acr_values`, `claims_locales` | Принимаются и игнорируются |
| `request`, `request_uri` | `request_not_supported` / `request_uri_not_supported` |
| `resource` | Для OAuth-клиентов MCP (§6); для OIDC-клиентов без ресурса — `invalid_target` |

Ответ — редирект на `redirect_uri` с `code`, `state` и `iss` (RFC 9207), в том числе для ошибок.

Порядок обработки:

1. Проверить клиента и `redirect_uri` (до этого — никаких редиректов).
2. Проверить остальные параметры; ошибки — редиректом с `error`.
3. Создать поток входа (10 минут, в БД; в cookie — случайный id потока).
4. Нет действующей сессии / `prompt=login` / превышен `max_age` → страница входа с названием и логотипом
   приложения («Вход в Семейную бухгалтерию»).
5. Нужно согласие (чужой клиент без сохранённого гранта, `prompt=consent`) → страница согласия (§7.3); для ресурса
   MCP — делегированное согласие (§6.4).
6. Выдать код (60 секунд, одноразовый, в БД — хеш) и отметить клиента участником сессии (для back-channel logout).

### 4.3. Токен `POST /token`

- Только `application/x-www-form-urlencoded`. Ответ ≤ 1 с в норме (у Claude лимит 10 с на обмен кода).
- Аутентификация клиента: `client_secret_basic`, `client_secret_post` (конфиденциальные), `none` (публичные).
  Сравнение секрета — за постоянное время.
- `authorization_code`: код, `redirect_uri`, `code_verifier` (S256). Повтор кода → `invalid_grant` и отзыв всех
  токенов, выданных по этому коду (OAuth 2.1 §4.1.3).
- `refresh_token`: ротация на каждое использование. Если старый токен предъявлен повторно:
  - в течение **5 секунд** после ротации тем же клиентом — выдаётся ещё одна пара (параллельные запросы
    одного клиента);
  - позже — признак кражи: грант отзывается целиком, все его токены перестают действовать, событие в журнал.
- `scope` при обновлении шире выданного → `invalid_scope`. `resource` при обновлении ≠ ресурсу гранта →
  `invalid_target`.
- Мёртвый, отозванный или чужой refresh-токен → `invalid_grant` (требование Claude).

| Токен | Формат | Срок |
| --- | --- | --- |
| Код авторизации | случайные 256 бит, в БД хеш | 60 с |
| ID-токен | JWT (`EdDSA` / `RS256`) | 15 мин |
| Access-токен | непрозрачный, 256 бит, префикс `fid_at_`, в БД хеш | 1 час |
| Refresh-токен | непрозрачный, 256 бит, префикс `fid_rt_`, в БД хеш | OIDC-клиенты: 30 дней с последнего использования; MCP: 60 дней; не дольше жизни гранта |

Access-токены непрозрачные, их проверяют интроспекцией ([ADR-0005](adr/0005-opaque-tokens.md)): отзыв действует
сразу, серверам ресурсов не нужны ключи. Refresh-токены выдаются, если у клиента в конфигурации разрешён grant
`refresh_token` (бухгалтерии он не нужен), и всегда — MCP-клиентам.

### 4.4. ID-токен и UserInfo

ID-токен: `iss`, `sub`, `aud` (= `client_id`), `exp`, `iat`, `auth_time`, `nonce` (если был), `amr`, `sid`,
и при `scope=profile` — `name`, `preferred_username` (если задано), `locale`, `updated_at`. `email` и
`email_verified` — только с v2 и только для подтверждённого адреса.

`GET|POST /userinfo` — `Authorization: Bearer` (и параметр `access_token` в теле POST по RFC 6750 §2.2; в query —
никогда). Отдаёт те же claims профиля, что ID-токен. Токен, выданный для ресурса MCP, в UserInfo не принимается.

### 4.5. Отзыв и интроспекция

- `POST /revoke` (RFC 7009): access- или refresh-токен своего клиента; отзыв refresh-токена отзывает грант.
  Неизвестный токен → `200` (по RFC).
- `POST /introspect` (RFC 7662): только для аутентифицированных клиентов. `active: true` возвращается, только если
  вызывающий — владелец ресурса, указанного в `aud` токена, или клиент, которому выдан токен. Ответ: `active`,
  `sub`, `client_id`, `scope`, `aud`, `exp`, `iat`, `iss`, `token_type`, плюс claims, которые приложение-ресурс
  положило в грант при согласии (например, `project_id`).

### 4.6. Свои и чужие клиенты

- Свой клиент (`first_party = true`): согласие не спрашивается, scope ограничен списком из конфигурации.
- Чужой OIDC-клиент: при первом входе — страница согласия «Приложение X получит ваше имя»; решение
  запоминается в гранте и отзывается в кабинете.

## 5. Выход и события для приложений

### 5.1. RP-Initiated Logout 1.0 (v1.1)

`GET|POST /logout` с `id_token_hint`, `client_id`, `post_logout_redirect_uri`, `state`, `ui_locales`.

- Клиент известен (по `client_id` или `aud` из `id_token_hint`) и `post_logout_redirect_uri` зарегистрирован у
  него → сессия закрывается **без экрана подтверждения**, редирект на адрес с `state`.
- `id_token_hint` не обязателен (бухгалтерия передаёт только `client_id`) — в отличие от Rauthy.
- Клиент неизвестен или адрес не зарегистрирован → страница «Выйти из family-id?»; после выхода — страница
  «Вы вышли» без редиректа.
- Закрывается текущая SSO-сессия браузера; всем приложениям, где она участвовала, уходит back-channel logout —
  это и есть «вышел в одном — вышел во всех» в этом браузере.

Выход без подтверждения позволяет чужому сайту разлогинить пользователя ссылкой. Ущерб — повторный вход в одно
касание, и это требование задачи. Мера: такой выход возможен только с зарегистрированным адресом возврата.

### 5.2. Back-Channel Logout 1.0 (v1.1)

- У клиента в конфигурации `backchannel_logout_uri` (HTTPS; в разработке — http на внутренний адрес).
- Поводы: выход в приложении (RP-initiated), выход в кабинете, «Выйти везде», закрытие сессии на странице
  устройств, сессия восстановления, удаление и блокировка аккаунта, обнаружение кражи refresh-токена.
- Logout token: JWT `typ: logout+jwt`, `iss`, `aud`, `iat`, `exp` (2 минуты), `jti`, `sub`, `sid`,
  `events: {"http://schemas.openid.net/event/backchannel-logout": {}}`, без `nonce`.
- Доставка: `POST application/x-www-form-urlencoded`, `logout_token=…`, таймаут 5 с, без редиректов. Через
  outbox в БД: повтор с растущей паузой (10 с … 15 мин) в течение часа, каждый раз с новым токеном. Неуспех — в
  журнал администратора; выход в family-id от этого не откатывается.

### 5.3. Событие «аккаунт удалён» (v1.1)

Security Event Token (RFC 8417) с событием RISC `https://schemas.openid.net/secevent/risc/event-type/account-purged`,
доставка push-методом RFC 8935 (`POST application/secevent+jwt`) на `events_uri` клиента. `aud` = `client_id`,
`sub_id` в формате `{"format": "iss_sub", "iss": …, "sub": …}`. Повторы — как у logout token, до 7 дней. Тот же
канал позже можно использовать для блокировки аккаунта (`account-disabled`).

Это заменяет вызов Admin API Rauthy, которым бухгалтерия сейчас удаляет пользователя.

## 6. Сервер авторизации OAuth 2.1 для MCP

Реализуется в v1.2, таблицы и порты закладываются в v1. Сверено со спецификацией MCP 2026-07-28 и требованиями
Claude к коннекторам (claude.com/docs/connectors/building/authentication) 15.10.2026.

### 6.1. Метаданные

Те же `/.well-known/oauth-authorization-server` и `/.well-known/openid-configuration` плюс
`client_id_metadata_document_supported: true`. `token_endpoint_auth_methods_supported` содержит `none` — без этого
Claude не использует CIMD. `offline_access` в `scopes_supported` не объявляется: refresh-токен MCP-клиенты получают
и так.

Метаданные защищаемого ресурса (RFC 9728, `/.well-known/oauth-protected-resource`) и ответ `401` с
`WWW-Authenticate: Bearer resource_metadata="…"` отдаёт **приложение-ресурс** (бухгалтерия), а не family-id.
В `authorization_servers` у ресурса должен быть **первым** issuer family-id (Claude берёт только первый), `resource`
— URL MCP-сервера дословно, как его вводит пользователь. Это описывается в `docs/integrate.md`.

### 6.2. Клиенты

1. **CIMD** (Client ID Metadata Document): `client_id` — HTTPS-URL с путём. Документ скачивается, только если хост
   в белом списке (`cimd.allowed_hosts`, сначала `claude.ai`); без редиректов; ≤ 16 КБ; таймаут 5 с; IP-адрес
   назначения не из частных и служебных диапазонов (защита от SSRF поверх белого списка); кэш по
   `Cache-Control`, но не дольше 24 часов. Проверки: валидный JSON, `client_id` совпадает с URL посимвольно,
   есть `client_name` и `redirect_uris`, `token_endpoint_auth_method` = `none` (иное — `invalid_client`).
2. **Предзаведённые публичные клиенты** — в конфигурации.
3. Динамической регистрации (`registration_endpoint`) нет.

`redirect_uri` должен совпасть с одним из `redirect_uris` клиента **и** с глобальным белым списком
`cimd.allowed_redirect_uris`: `https://claude.ai/api/mcp/auth_callback`, `http://localhost/callback`,
`http://127.0.0.1/callback`. Для loopback-адресов порт не сравнивается (Claude Code открывает случайный порт).

### 6.3. Ресурсы (RFC 8707)

- Ресурсы заведены в конфигурации: `uri` (канонический URL MCP-сервера), приложение-владелец (OIDC-клиент с
  секретом), адрес страницы делегированного согласия, допустимые `scope`.
- `resource` обязателен в запросе авторизации и в обмене кода для MCP-клиентов; сравнение — посимвольное после
  приведения схемы и хоста к нижнему регистру. Неизвестный ресурс → `invalid_target`.
- Один токен — один ресурс: `aud` = `uri` ресурса. Интроспекция отдаёт `active: true` только владельцу этого
  ресурса, поэтому токен, выданный для одного ресурса, другим не принимается.

### 6.4. Делегированное согласие

Образец — consent flow Ory Hydra ([ADR-0007](adr/0007-mcp-delegated-consent.md)).

```
Claude ──/authorize?resource=R──► family-id ── вход (passkey / SSO-сессия)
                                     │
                                     ├─ consent_request: challenge (10 мин, одноразовый)
                                     ▼
          браузер ──► R.consent_url?consent_challenge=… (страница бухгалтерии: проект, права)
                                     │
   бухгалтерия (сервер) ──GET  /api/consent/{challenge}──────────► family-id   (Basic: client_id/secret владельца R)
   бухгалтерия (сервер) ──POST /api/consent/{challenge}/accept──► family-id   {scope, claims: {project_id}, remember}
                                     ◄── {redirect_to: https://id.<домен>/authorize/resume?consent_verifier=…}
          браузер ──► family-id: verifier + та же SSO-сессия ──► код ──► https://claude.ai/api/mcp/auth_callback?code&state&iss
```

- `GET /api/consent/{challenge}` отдаёт: клиента (`client_id`, `client_name`, хост `redirect_uri`, признак
  «только loopback»), `sub` и имя пользователя, запрошенные `scope`, ресурс. Читать и отвечать может только
  владелец ресурса.
- `accept`: итоговые `scope` (подмножество запрошенных и допустимых для ресурса), `claims` (≤ 2 КБ JSON, попадают
  в интроспекцию), `remember` (не спрашивать повторно, пока грант жив и новые `scope` ⊆ прежних).
  `reject`: `error` (`access_denied`), `error_description`.
- `consent_verifier` одноразовый и привязан к SSO-сессии, в которой начат поток: открыть ссылку в другом браузере
  нельзя.
- Страница согласия приложения **обязана** показать название клиента и хост `redirect_uri`, а для loopback-клиентов —
  предупреждение «приложение на этом компьютере» (MUST спецификации MCP). Готовый фрагмент шаблона и чек-лист — в
  `docs/integrate.md`.

### 6.5. Токены MCP

Access — 1 час, непрозрачный, проверка интроспекцией (у ресурса кэш ≤ 60 с). Refresh — ротация, 60 дней с
последнего использования, повтор → отзыв гранта, `scope` шире выданного → `invalid_scope`. Грант виден в кабинете
в «Подключённых приложениях и ассистентах» и отзывается там (отзыв мгновенный за счёт интроспекции).

## 7. Страницы и сценарии

Все страницы — серверный рендер (Askama), работают без JS, кроме WebAuthn-ceremony. Мобильная вёрстка первой.

### 7.1. Вход `/login`

- Шапка: логотип и название приложения-клиента («Вход в Семейную бухгалтерию»), если вход начат приложением;
  иначе — название сервиса.
- Основная кнопка «Войти с passkey»; поле с автоподстановкой passkey; ссылка «Создать аккаунт»; v1.1 — кнопка
  «Войти через Telegram».
- Ошибки ceremony (отмена, таймаут, нет passkey) — человеческим языком: «Вход отменён. Попробуйте ещё раз или
  войдите с другого устройства».
- Переключатель языка в подвале; ссылка «Не получается войти?» → страница с вариантами восстановления.

### 7.2. Регистрация `/register`

Имя → «Создать passkey» → предложение второго способа (§3.3) → возврат в поток приложения или в кабинет.

### 7.3. Согласие `/consent`

Только для чужих OIDC-клиентов: «Приложение X (хост) просит: ваше имя и язык». Кнопки «Разрешить» /
«Отклонить». Для MCP-ресурсов — делегированное согласие на странице приложения (§6.4).

### 7.4. Выход `/logout`

Подтверждение только для неизвестного клиента (§5.1). После выхода без адреса возврата — «Вы вышли».

### 7.5. Личный кабинет `/account`

| Раздел | Содержание | Версия |
| --- | --- | --- |
| Профиль | Имя, имя пользователя, язык, тема. Смена имени → WebAuthn Signal API `signalCurrentUserDetails` | v1 |
| Способы входа | Passkey: название (автоматически по AAGUID — «iCloud Keychain», «Google Password Manager»; можно переименовать), создан, последний вход, «синхронизируется». Добавить passkey на этом устройстве, удалить (не последний способ). v1.1 — Telegram: привязать/отвязать | v1 / v1.1 |
| Устройства и сессии | Браузер и ОС (из User-Agent), IP с маской (`203.0.113.x`), начало и последняя активность, «это устройство»; «Выйти на этом устройстве», «Выйти на всех остальных», «Выйти везде» — с back-channel logout | v1 (back-channel — v1.1) |
| Подключённые приложения и ассистенты | Клиенты с грантами и сессиями, ресурс и права у MCP, последний доступ; «Отозвать» | v1.1 / v1.2 |
| Журнал безопасности | События за год: входы, новые и удалённые способы, сессии, гранты, восстановление, обнаружение кражи токена | v1 |
| Удаление аккаунта | §3.6 | v1.1 |

Действия, меняющие способы входа, сессии других устройств и аккаунт, требуют свежей аутентификации (≤ 10 мин).

### 7.6. Служебные страницы

Ошибки 400/403/404/429/500 и «ссылка устарела» — в стиле сервиса, на языке пользователя, с кодом ошибки для
поддержки (`request_id`). Ошибки протокола, которые нельзя вернуть приложению (неверный `redirect_uri`,
неизвестный клиент), показываются здесь же.

## 8. Языки и дизайн

### 8.1. Языки

- ru / en / th: все страницы, сообщения об ошибках, письма (v2), даты и числа в формате языка (как
  `kernel::web::date_in` бухгалтерии).

- Строки — словари в коде, как в бухгалтерии: `Tr(ru, en, th)` — пропустить перевод нельзя, это ошибка компиляции.
- Тайские строки помечаются `// th-review` до проверки носителем; `make i18n-th-report` выводит непроверенные.

### 8.2. Дизайн

- Как у бухгалтерии: токены `styles/app.css` (светлая и тёмная тема), `tailwind.config.cjs`, Inter + Noto Sans
  Thai (свои файлы шрифтов), один акцент — индиго, иконки Lucide. Тема по системе, переключатель в кабинете.
- Мобильная вёрстка первой, цели нажатия ≥ 44 px, WCAG 2.1 AA (контраст, фокус, подписи полей, `aria-live` для
  ошибок ceremony, работа с клавиатуры).
- Без JS-фреймворков: Askama + `webauthn.js` (своё, ~5 КБ: base64url, conditional UI, регистрация, Signal API).
  htmx — только если понадобится в кабинете.
- Статика собирается `make assets` (Node в контейнере) и коммитится, вшивается в бинарник с хешем в имени и кэшем
  на год. Rust-сборке Node не нужен.
- Логотипы приложений-клиентов — файлы в каталоге конфигурации, отдаются самим сервисом. Логотипы по URL из CIMD не
  показываются (трекинг, CSP) — вместо них буква на круге.

## 9. Модель данных

## 11. Архитектура

Эталон `rust-hex-api` (v2): Cargo workspace, фича = крейт, порты и адаптеры, связки в `crates/app/src/wiring`.
Отклонения и расширения — [ADR-0001](adr/0001-architecture.md).

```
crates/kernel        ошибки, config (TOML + env + *_FILE), crypto (токены, хеши, HMAC, AEAD), i18n, web
                     (PageCtx, каркас, рендер, ошибки, заголовки, CSP, статика), auth (сессия из cookie, CSRF,
                     свежая аутентификация), throttle (лимиты), audit (порт журнала), request (IP за прокси, Host)
crates/features/
  keys               ключи подписи: генерация, шифрование, ротация, JWKS, подпись JWT
  audit              журнал безопасности: запись (реализация порта kernel), чтение для кабинета, чистка
  accounts           аккаунт, профиль, удаление, блокировка, ссылки восстановления
  passkeys           WebAuthn: регистрация, вход, повторная аутентификация, список и имена passkey
  sessions           SSO-сессии, потоки входа, свежая аутентификация, устройства, «выйти везде»
  oidc               протокол: клиенты из конфигурации, authorize/token/userinfo/revoke/introspect/logout,
                     гранты, коды, токены, согласие, back-channel logout и SET через outbox
  mcp_clients        v1.2: CIMD-клиенты, реестр ресурсов, API делегированного согласия
  upstream           v1.1: порт UpstreamProvider; адаптеры generic OIDC (Telegram, потом Google/LINE/Apple)
                     и OAuth2 (GitHub/Facebook — v2); связанные учётки
  portal             все страницы: вход, регистрация, согласие, выход, восстановление, кабинет
crates/app           main, CLI (serve, migrate, recovery-link, keys rotate, users …), wiring, фоновые задачи,
                     статика
```

Связи (потребитель объявляет порт, адаптер — в `app/wiring`):

| Потребитель | Порт | Поставщик |
| --- | --- | --- |
| passkeys | `AccountDirectory` (создать аккаунт, найти по handle) | accounts |
| sessions | `AccountStatus` (активен ли) | accounts |
| oidc | `SessionLookup`, `SessionParticipants`; `AccountClaims`; `TokenSigner`; `ClientResolver`, `ResourceRegistry` (v1.2) | sessions; accounts; keys; mcp_clients |
| accounts | `AccountErasure` (удалить способы, сессии, гранты, разослать события) | passkeys, sessions, oidc, upstream |
| sessions | `SessionEnded` (сессия закрыта → back-channel logout) | oidc |
| upstream | `AccountDirectory`, `SessionStarter` | accounts, sessions |
| portal | порты ко всем сценариям | все фичи |

Каждая фича тестируется отдельно (`cargo test -p <фича>`) с memory-репозиториями и фейковыми портами. Фичи
`upstream`, `mcp_clients` и провайдеры (`telegram`, …) — Cargo-флаги приложения. Сборка для Conformance Suite —
флаг `conformance` (тестовый вход), в выпускаемый образ он не входит.

Стек: Rust 2024, Axum 0.8, Askama 0.16, sqlx 0.8 (PostgreSQL), tokio, `webauthn-rs` 0.5 (Passkey API, флаги
`conditional-ui` и `danger-allow-state-serialisation` — состояние ceremony хранится в БД), `jsonwebtoken` (EdDSA,
RS256), `openidconnect` 4 (клиент для Telegram и других провайдеров), `reqwest` (rustls), `aes-gcm`, `tower-http`.
Точные версии и возможности сверяются в начале этапа 1. sqlx 0.9 уже вышел (май 2026); остаёмся на 0.8, как требует
задача и как в бухгалтерии, переход — отдельным решением.

`webauthn-rs` тянет OpenSSL. В образ — статическая сборка (`openssl/vendored`) или `libssl` из базового образа;
решение и размер образа — на этапе 0, после сравнения.

## 12. Конфигурация

Файл TOML (`/etc/family-id/config.toml`, путь — `FID_CONFIG`) — клиенты, ресурсы, белые списки, сроки. Переменные
окружения переопределяют скалярные значения (`FID_…`). Секреты — только из окружения или из файлов `*_FILE`
(`FID_DATABASE_URL_FILE=/run/secrets/db_url`), в TOML — ссылки на имя переменной, не значения.

```toml
[server]
public_url = "https://id.example.com"      # issuer; без пути и завершающего /
bind = "0.0.0.0:8090"
trust_proxy = true                         # IP клиента из X-Forwarded-For (только за Caddy)

[brand]
name = { ru = "Семейный вход", en = "Family ID", th = "Family ID" }   # th-review

[webauthn]
rp_id = "example.com"                      # корневой домен; public_url должен быть его поддоменом
rp_name = "Family ID"

[session]
idle_days = 30
max_days = 90
reauth_minutes = 10

[[clients]]
id = "family-budget"
name = { ru = "Семейная бухгалтерия", en = "Family Budget", th = "บัญชีครอบครัว" }   # th-review
logo = "logos/family-budget.svg"
first_party = true
secret_env = "FID_CLIENT_FAMILY_BUDGET_SECRET"
redirect_uris = ["https://budget.example.com/auth/callback"]
post_logout_redirect_uris = ["https://budget.example.com/"]
backchannel_logout_uri = "https://budget.example.com/auth/backchannel-logout"
events_uri = "https://budget.example.com/auth/events"
scopes = ["openid", "profile"]
grant_types = ["authorization_code"]
id_token_signed_response_alg = "EdDSA"

[[resources]]                              # v1.2
uri = "https://budget.example.com/mcp"
owner_client = "family-budget"
consent_url = "https://budget.example.com/mcp/consent"
scopes = ["budget:read", "budget:write"]

[cimd]                                     # v1.2
allowed_hosts = ["claude.ai"]
allowed_redirect_uris = ["https://claude.ai/api/mcp/auth_callback", "http://localhost/callback", "http://127.0.0.1/callback"]
```

Секреты окружения: `FID_DATABASE_URL`, `FID_KEY_ENCRYPTION_KEY` (32 байта, base64 — шифрует закрытые ключи
подписи), `FID_COOKIE_SECRET` (≥ 32 байта — HMAC для CSRF и подписанных cookie), секреты клиентов,
`FID_TELEGRAM_CLIENT_SECRET` (v1.1).

**Продакшен не стартует** (`FID_ENV=prod`), если: `public_url` не `https://`; не заданы или коротки
`FID_KEY_ENCRYPTION_KEY`, `FID_COOKIE_SECRET`, секрет любого конфиденциального клиента; `rp_id` не является
суффиксом хоста `public_url`; у клиента `redirect_uri` не `https` (кроме loopback публичных клиентов); включены
`SWAGGER` или сборка `conformance`. Сообщение называет, что именно не так.

## 13. Безопасность: угрозы и меры

Цель — OWASP ASVS 5.0 уровня 2. Отдельная таблица соответствия ASVS — `docs/security.md` на этапе 1.

### 13.1. Веб-слой

| Угроза | Меры |
| --- | --- |
| Кража сессии | Cookie `__Host-fid_session`: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`; id 256 бит, в БД хеш; новая сессия на каждый вход (фиксация невозможна); простой 30 дней, максимум 90 дней; свежая аутентификация ≤ 10 мин для опасных действий |
| CSRF | HMAC-токен в каждой форме и в заголовке `X-CSRF-Token` для `fetch` + проверка `Origin`; протокольные `POST /token`, `/revoke`, `/introspect` — без cookie, CSRF к ним неприменим |
| XSS | Askama экранирует по умолчанию; CSP `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; form-action 'self' <origin redirect_uri клиента>; frame-ancestors 'none'; base-uri 'none'` — без `unsafe-inline`/`unsafe-eval`. `form-action` дополняется origin'ом клиента на страницах, форма которых завершается редиректом к нему (иначе Chrome блокирует редирект после POST) |
| Clickjacking | `frame-ancestors 'none'`, `X-Frame-Options: DENY` |
| Прочие заголовки | HSTS (2 года, `includeSubDomains` — решение владельца домена, по умолчанию без), `nosniff`, `Referrer-Policy: no-referrer` (коды и токены не утекают через Referer), `Permissions-Policy`, `Cross-Origin-Opener-Policy: same-origin`, `Cache-Control: no-store` для всех ответов с токенами и персональными данными |
| Подмена Host | Запросы с `Host` ≠ хосту `public_url` → `421` |
| Перебор и DoS | Лимиты в памяти: по IP, по аккаунту, по клиенту (вход, регистрация, ceremony, `/token`, `/introspect`, API согласия, ссылки восстановления); 429 + `Retry-After`. Тело ≤ 64 КБ, таймаут запроса 15 с, исходящих — 5 с |
| Утечки в логах | Токены, коды, `code_verifier`, cookie и `Authorization` в логи не пишутся; IP в журнале — с маской |
| Перечисление аккаунтов | Логинов нет: вход по discoverable passkey, перечислять нечего. Занятость имени пользователя видна только вошедшему в форме кабинета, с лимитом запросов |

### 13.2. Passkey

| Угроза | Меры |
| --- | --- |
| Фишинг | Origin в `clientDataJSON` — строго `public_url`; `rpId` — корневой домен, но другие поддомены не входят в список допустимых origin |
| Повтор ответа | Одноразовый challenge с TTL 5 мин, состояние ceremony на сервере |
| Клон ключа | Счётчик подписи от webauthn-rs; уменьшение у не-синхронизируемого passkey → отказ и событие в журнал |
| Слабая проверка пользователя | UV обязательна (Passkey API) |
| Захват аккаунта через новый способ | Привязка только из вошедшей сессии со свежей аутентификацией; уведомление в журнал |

### 13.3. OAuth 2.1 и RFC 9700

На каждую атаку из RFC 9700 — отдельный тест (`crates/features/oidc/tests/rfc9700_*.rs`). Номера разделов
сверяются с текстом RFC на этапе 1.

| Атака (RFC 9700) | Мера сервера | Тест |
| --- | --- | --- |
| 4.1 Недостаточная проверка redirect URI | Точное совпадение; loopback — только порт; ошибка — страница, не редирект | подмена пути, поддомена, query, фрагмента, схемы |
| 4.2 Утечка через Referer | `Referrer-Policy: no-referrer` на всех страницах | заголовок на `/authorize`, `/login`, `/consent` |
| 4.3 Утечка через историю браузера | Коды одноразовые 60 с; токены только в ответе `/token`; ничего в query, кроме кода | токен в query отвергается |
| 4.4 Mix-up | `iss` в каждом ответе авторизации (RFC 9207) | `iss` есть и в ошибках |
| 4.5 Внедрение кода | PKCE S256 обязателен; код привязан к клиенту и `redirect_uri` | чужой verifier, без verifier, чужой клиент |
| 4.6 Внедрение access-токена | Атака на клиента; со стороны сервера — токен привязан к ресурсу (`aud`) и клиенту (`client_id` в интроспекции); рекомендации клиентам — в integrate.md | интроспекция возвращает `client_id` и `aud` |
| 4.7 CSRF | `state` возвращается как есть; PKCE; CSRF-токены на формах | — |
| 4.8 Понижение PKCE | `code_challenge_method` только `S256`; verifier без challenge → `invalid_grant` | `plain`, отсутствующий challenge |
| 4.9 Утечка токена на сервере ресурса | `aud` = ресурс, интроспекция только владельцу ресурса | токен ресурса A у ресурса B |
| 4.10 Использование украденного токена | Короткий access (1 ч), отзыв мгновенный (интроспекция) | отозванный токен неактивен |
| 4.11 Открытый редирект | Неизвестный клиент или `redirect_uri` — страница ошибки; `post_logout_redirect_uri` — только зарегистрированный | — |
| 4.12 Редирект 307 | Только `303 See Other` после POST | код ответа после POST-форм |
| 4.13 Прокси с терминацией TLS | IP из `X-Forwarded-For` только при `trust_proxy` и только от Caddy на loopback | подделанный заголовок без доверия |
| 4.14 Защита refresh-токенов | Ротация, обнаружение повтора, отзыв гранта, срок с последнего использования | повтор после окна → грант отозван |
| 4.15 Клиент выдаёт себя за пользователя | client_credentials нет; `client_id` задаёт только конфигурация или URL CIMD — с `sub` аккаунтов (UUID) не пересекается | `client_id` в виде UUID отвергается конфигурацией |
| 4.16 Clickjacking | `frame-ancestors 'none'` | заголовок на страницах согласия |
| 4.17 In-browser communication | `postMessage`-режимов ответа нет, `response_mode` только `query` | `web_message`/`form_post` отвергаются |
| 4.18 Редирект на фишинговый сайт | Клиенты — только из конфигурации и CIMD с белого списка хостов и redirect URI; ошибки до проверки клиента и `redirect_uri` не редиректят | ошибка с неизвестным клиентом — страница, не редирект |

Плюс: implicit и password grant (`unsupported_response_type`, `unsupported_grant_type`); секрет у публичного
клиента → `invalid_client`; токен в query string не принимается.

### 13.4. MCP и CIMD

SSRF при скачивании CIMD (белый список хостов, запрет частных адресов, без редиректов, лимиты размера и времени);
подмена клиента через loopback (обязательное предупреждение на странице согласия, показ хоста); confused deputy
(согласие на каждый ресурс отдельно, `aud`); передача токена дальше (в integrate.md: MCP-сервер не передаёт
полученный токен в другие API).

### 13.5. Ключи и данные

Закрытые ключи подписи — в БД, зашифрованы AES-256-GCM мастер-ключом из окружения (копия базы без мастер-ключа
бесполезна для подделки токенов). Резервные копии базы — зашифрованы age. Пользователь БД — без суперправ.
Журнал безопасности — 1 год, затем удаляется.

## 14. Нефункциональные требования

- **Память:** < 64 МБ RSS в покое (проверяется в CI: запуск контейнера, 30 с простоя, `docker stats`). Пул БД
  ≤ 5 соединений, кэши ограничены по размеру.
- **Производительность:** `/token` и `/authorize` ≤ 50 мс на p95 без учёта сети; хеширование токенов — SHA-256
  (Argon2 не нужен: токены случайные 256 бит).
- **Один экземпляр.** Лимиты и кэши в памяти; при перезапуске они обнуляются — допустимо. Всё, что должно
  пережить перезапуск (сессии, гранты, outbox), — в БД.
- **Образ:** многоархитектурный (amd64/arm64) в GHCR `ghcr.io/yolshin195/family-id`, пользователь без root,
  read-only rootfs, healthcheck.
- **Логи:** структурированные (JSON в prod), `request_id` в каждом ответе и на страницах ошибок.
- **Доступность:** IPv4 обязателен (требование Claude), IPv6 — если есть у сервера.

  оно же пример для `docs/integrate.md`), по желанию — бухгалтерия из её образа (после её доработки, §17).
  `make` — собрать и запустить, `make dev` — БД в контейнере + `cargo run`.
- **Продакшен:** тот же VDS, Caddy на хосте: `id.<домен>` → `127.0.0.1:8090`. Контейнер подключается к сети
  существующего PostgreSQL (имя сети — в настройках), своя база `family_id` и пользователь `fid_app` создаются
  скриптом `deploy/postgres/create-db.sh`.
- **Резервные копии:** `make backup` по cron — `pg_dump` базы `family_id`, шифрование age, три копии (свежая,
  1–6 дней, 7–12 дней); `make restore-check` раз в месяц восстанавливает копию во временную базу и проверяет
  схему и число аккаунтов. Без мастер-ключа (`FID_KEY_ENCRYPTION_KEY`) копия не позволяет подписывать токены —
  мастер-ключ хранится отдельно, в менеджере паролей.
- **Обновление и откат:** образ по тегу `sha-<коммит>`, миграции только вперёд и совместимые с предыдущей версией
  на время отката.
- **Документация** (на русском): `README.md`, `docs/deploy.md`, `docs/integrate.md` (подключить проект за
  10 минут), `docs/security.md` (ASVS), `docs/operations.md` (CLI, ротация ключей, восстановление доступа).

## 17. Интеграция с бухгалтерией и переезд с Rauthy

### 17.1. Что работает без изменений бухгалтерии

Адрес провайдера (`OIDC_ISSUER=https://id.<домен>`), discovery, PKCE, `nonce`, проверка ID-токена по JWKS
(`openidconnect` 4 берёт алгоритмы из метаданных — EdDSA поддерживается), `amr` для «Требовать 2FA», выход через
`end_session_endpoint` с `client_id` и `post_logout_redirect_uri`.

### 17.2. Что надо поменять в бухгалтерии (позже, отдельной задачей; описание — в `docs/integrate.md`)

1. **Email необязателен.** Сейчас `verify_id_token` (`crates/features/projects/src/adapters/oidc.rs`) отвергает
   ID-токен без `email`, а `fb_users.email` — `NOT NULL`. Пока это не исправлено, бухгалтерия не пустит
   пользователей family-id (почты у них до v2 нет). Приглашения по ссылке уже есть (миграция
   `20261015145556_project_invites`), добавление участника по email остаётся для тех, у кого email есть.
2. **Удаление аккаунта** — по событию `account-purged` (§5.3) вместо Admin API Rauthy.
3. **Back-channel logout** — эндпоинт, закрывающий сессии бухгалтерии по `sid`/`sub`.
4. **SSO без нажатий** — при заходе на защищённую страницу без своей сессии бухгалтерия делает
   `/authorize?prompt=none`; `login_required` → обычная страница входа.
5. **MCP (v1.2)** — метаданные ресурса, `401` с `resource_metadata`, интроспекция с кэшем ≤ 60 с, страница
   делегированного согласия (выбор проекта и прав).
6. **Переезд с Rauthy** — на время перехода два провайдера; `fb_users.rauthy_sub` → таблица связей
   (`provider`, `sub`).

### 17.3. Переезд пользователей

На время перехода бухгалтерия принимает оба провайдера. Вошедший через Rauthy пользователь нажимает «Перейти на
новый вход» → регистрируется или входит в family-id → бухгалтерия связывает новый `sub` с тем же пользователем.
Passkey Rauthy (rpId `auth.<домен>`) перенести нельзя: пользователь создаёт новый. Когда все перешли — Rauthy
выключается, его база удаляется после контрольной копии.
