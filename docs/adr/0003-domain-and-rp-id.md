# ADR-0003. Домен из конфигурации, rpId — корневой домен

Статус: предложено, 15.10.2026. Решение владельца: «rpId = корневой домен», «домен должен настраиваться».

## Контекст

Passkey привязан к `rpId`: смена `rpId` делает все passkey недействительными. WebAuthn разрешает `rpId`, равный
origin страницы или его регистрируемому суффиксу. Технический домен хостера использовать нельзя: его нельзя
считать своим навсегда.

## Решение

- В коде нет конкретного домена. `server.public_url` (`https://id.<домен>`) — issuer и единственный допустимый
  origin; `webauthn.rp_id` — корневой `<домен>`.
- При старте проверяется, что хост `public_url` равен `rp_id` или оканчивается на `.` + `rp_id`; иначе сервис не
  стартует.
- Список допустимых origin для WebAuthn — только `public_url`. Другие поддомены (`budget.<домен>`) passkey-ceremony
  у нас пройти не могут, хотя `rpId` у них общий.
- Документы и примеры используют `example.com`.

## Последствия

- Passkey переживают переезд сервиса на другой поддомен (`id.` → `auth.`), в менеджере паролей виден понятный
  `<домен>`.
- Приложения на поддоменах технически могут запросить у браузера подпись для того же `rpId`, но сервер такую
  подпись не примет из-за origin. Если позже понадобится принимать passkey прямо в приложениях, это отдельное
  решение (список origin).
- Смена корневого домена потребует новых passkey — это фиксируется в `docs/deploy.md`.

## Отвергнутые варианты

- `rpId = id.<домен>` — строже, но смена поддомена ломает все passkey.
- Related Origin Requests (`/.well-known/webauthn`) — не нужны, пока все приложения на одном корневом домене.
